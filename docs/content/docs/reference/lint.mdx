Read this to know what the Issues view reports and why, or to add a rule.

## What it checks

The rules follow what the site does, not a style guide: the site turns many
mistakes into plain text or a placeholder instead of failing the build, so
they would otherwise only show on the page. The one style rule,
`emphasis-marker`, keeps the markers the editor writes.

The sidebar's Issues view shows the open note's issues, checked about
400 ms after typing stops (`src/features/lint/useLint.ts`) and again when another
file changes on disk. The toolbar shows the count and opens the view;
picking an issue opens Source with the problem selected and marked. The
frontmatter is blanked before the note is parsed, so no rule reports in it;
`notesPageSchema` checks it in the frontmatter form instead (see
[Editor](../guide/using.mdx#editor)).

The rules live in `server/services/lint/` (`lint.ts` runs them, `rules/` holds them)
and run on `POST /api/lint`, which writes nothing. Code blocks and inline
code are never checked.

## Rules

| Rule | Level | Reports | Why |
| --- | --- | --- | --- |
| `callout-type` | error | `<Callout type>` outside fumadocs-ui's list (`info`, `warn`/`warning`, `error`, `success`, `idea`, and `tip`) | fumadocs-ui draws it with no icon and a muted colour. |
| `callout-style` | error | `<Callout style="…">` as a string | The site only reads a `style` object, so the string sets nothing; `type` picks the look. |
| `link-broken` | error | A relative link or link definition (`./`, `../`, `foo/bar`) that reaches no note, resolved like `source.resolveHref` (as a file next to the note, then as a URL against the page), and a link under the site's base URL with no page. A link to a file under the media folder is fine. | The link is dead on the site. |
| `asset-missing` | error | A `/…` image that is not in `public/`, and a `<Diagram>` with no `src` or no `diagrams/<src>.diagram.json` | The site shows a broken image or a placeholder. |
| `diagram-invalid` | error, warning | A `<Diagram>` file the site's checks (`packages/diagram/src/validate/validate.ts`) find wrong: an error when it cannot be laid out, a warning when it draws with a layout problem (nodes too close, a label that overflows) | An error shows a placeholder on the site; a warning draws badly. |
| `emphasis-marker` | warning | Emphasis or strong written with `_` / `__` | The notes use `*text*` / `**text**`, as the editor writes them, so a Visual edit does not rewrite them in a diff. |
| `mdx-parse` | error | The note does not parse | The site cannot build it, and no other rule can check it. |

## What the lint parses

Notes are parsed as fumadocs-mdx does by default: MDX with GFM. Directive
syntax (`:::note`, `:name[…]`) is not turned on, so it reads as plain text
and no rule checks it. A component no plugin knows is left to the site's
MDX build to report.

## Running it on every note

```sh
npm run docs:lint                                  # these docs
npm run lint:notes -w @fdbook/server -- <folder>   # another project
```

lints every note and exits 1 on an error (`server/bin/lint.ts`).
`tests/server/lint/notes.test.ts` keeps every page of the docs at
zero issues, warnings included.

## Adding a rule

Add it to `server/services/lint/rules/`, call it from `server/services/lint/lint.ts`, add its
name to `LintRule` in `server/services/lint/types.ts`, report the site's consequence in the message (as
the rules above do), add a test under `tests/server/lint/`, and add a row
here.
